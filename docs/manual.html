openserve User Manual

BYOC LLM serving — deploy open-source models inside your own cloud. Prompts never leave your VPC.

openserve is a Kubernetes-native platform for running open-source large language models (LLMs) inside a customer's own GCP project. Unlike managed-cloud inference providers, every prompt and response stays inside your infrastructure — openserve is the control plane, not the data plane for third-party systems.

This manual covers installation, day-to-day operations, the full REST API, and advanced configuration. For a quick overview, see the landing page.

ℹ️

Version: This manual documents openserve v1. AWS and Azure adapters are planned for v2/v3. Currently GCP (GKE) only.

Architecture

openserve consists of four components running inside the customer's Kubernetes cluster, plus GCP managed services the customer provisions:

Customer's GCP project
├─ GKE cluster
│  ├─ openserve-operator      Kubernetes controller (CRD reconciler)
│  ├─ openserve-control-api   REST API + OIDC auth + audit log
│  ├─ openserve-gateway       API key auth + rate limit + proxy
│  ├─ openserve-gui           Next.js web UI
│  └─ vllm-<model-id>        one pod per deployment, scale-to-zero
├─ Cloud SQL (Postgres 15+)   org/user/key/audit data, private IP only
├─ Memorystore (Redis 7)      rate-limit counters (RPM + TPM)
├─ GCS bucket                 model weight cache (CMEK encrypted)
└─ BigQuery                   token usage + spend telemetry

Request path: Internet → Cloud Armor → Load Balancer → gateway → vLLM pod. The gateway validates the API key (Postgres/Argon2id), checks rate limits (Redis sliding window), resolves the target pod (prefix-cache-aware consistent hash), and streams the response without buffering.

Components

operator

The operator is a Kubernetes controller that reconciles three custom resources (CRDs) into real GKE infrastructure:

  • ModelDeployment → creates a vllm-<name> Deployment + ClusterIP Service + KEDA ScaledObject + ConfigMap route entry
  • APIKey → syncs key metadata into the gateway's routing ConfigMap
  • BudgetPolicy → polls BigQuery spend every 5 min; scales to 0 when the daily/monthly cap is breached

control-api

The REST API consumed by the GUI and direct API clients. Handles OIDC login, org/member management, deployment CRUD, API key lifecycle, RAG document upload, audit log queries, and usage stats. Never handles inference traffic directly.

gateway

A Go reverse proxy that sits in front of every vLLM pod. For each request it: validates the API key, checks RPM/TPM rate limits, resolves the deployment → pod address, enforces token caps, proxies the SSE stream without buffering, and records actual token usage post-stream for accurate TPM tracking.

gui

A Next.js web application served at the domain root. Communicates only with the control-api (never directly with vLLM). Provides catalog browsing, one-click deployment, API key management, usage charts, member management, and audit log views.

Terraform GCP Setup

The examples/terraform/gcp-prereqs directory provisions all GCP prerequisites (VPC, Cloud SQL, Redis, GCS bucket, BigQuery dataset, Workload Identity bindings):

bash 
cd examples/terraform/gcp-prereqs
cp terraform.tfvars.example terraform.tfvars

# Edit terraform.tfvars — at minimum set:
gcp_project = "your-gcp-project-id"
region      = "us-central1"
domain      = "ai.acme.com"

terraform init
terraform plan
terraform apply   # ~8 min to provision all resources

Terraform outputs the values you need for helm install: postgres_host, redis_host, gcs_bucket.

Helm Install

bash 
helm repo add openserve https://charts.openserve.io
helm repo update

helm install openserve openserve/openserve \
  --namespace openserve-system --create-namespace \
  --set domain=ai.acme.com \
  --set google.clientId=YOUR_GOOGLE_CLIENT_ID \
  --set postgres.host=10.0.0.5 \
  --set postgres.secret=openserve-postgres-secret \
  --set redis.host=10.0.0.6 \
  --set gcs.bucket=acme-openserve-models \
  --set billing.bigqueryDataset=openserve_usage \
  --wait --timeout=5m
ℹ️

To use Okta, Azure AD, or another OIDC provider instead of Google, add --set oidc.issuerUrl=https://your-okta-domain.okta.com and --set oidc.clientId=.... See the OIDC section.

Upgrade

helm repo update
helm upgrade openserve openserve/openserve \
  --namespace openserve-system \
  --reuse-values

Uninstall

helm uninstall openserve --namespace openserve-system
# CRDs are NOT deleted by default — delete manually if desired:
kubectl delete crd modeldeployments.openserve.io apikeys.openserve.io budgetpolicies.openserve.io

Local Development

Run the entire stack locally with Docker Compose. No Kubernetes required — a mock vLLM server handles inference.

bash 
git clone https://github.com/openserve/openserve
cd openserve

# Copy the dev env file (DEV_EMAIL bypasses OIDC)
cp .env.dev.example .env.dev

# Build and start all services
docker compose --env-file .env.dev up --build

# Services:
#   control-api  → http://localhost:8080
#   gateway      → http://localhost:8081
#   gui          → http://localhost:3000
#   mock-vllm    → http://localhost:8000

Run the end-to-end demo script to validate the full flow:

bash hack/local-demo.sh
⚠️

Never use DEV_EMAIL in production. It bypasses all authentication. Set it only in .env.dev for local testing.

Model Catalog

The catalog ships ~25 vetted open-source models. Each entry includes the Hugging Face model ID, recommended GPU class, vLLM args, and a cosign-signed SHA256 weight digest.

Browse the catalog

curl https://ai.acme.com/api/v1/catalog \
  -H "Authorization: Bearer $TOKEN" | jq '.models[].id'

Request a new model

Open a GitHub issue using the Request a model template. The team vets the license, cosign-signs the manifest, and adds the catalog entry — typically within a few days.

ℹ️

Catalog YAML files live in catalog/models/. The weightDigestSha256 field is a placeholder in the repo; real values are computed and signed during the release process. The CI pipeline rejects PRs with unchecked placeholder values.

Deployments

A ModelDeployment is a Kubernetes CRD that represents a deployed model. The operator reconciles it into a vLLM Deployment + Service + KEDA ScaledObject.

Create a deployment (GUI)

1

Open the Catalog tab

Browse the list of available models. Each card shows GPU class, parameter count, and estimated cost/hour.

2

Click "Deploy"

Configure GPU class, scale-to-zero, idle timeout, replicas, and daily budget cap.

3

Wait for phase=Running

The operator downloads and verifies the weights (~2–4 min for 8B, ~8–12 min for 70B). Phase transitions: Pending → Pulling → Verifying → Running.

Create a deployment (API)

bash
curl -X POST https://ai.acme.com/api/v1/deployments \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "modelRef":       "llama-3-8b-instruct",
    "gpuClass":       "l4",
    "scaleToZero":    true,
    "idleTimeoutMin": 10,
    "minReplicas":    0,
    "maxReplicas":    2,
    "budget":  { "dailyUsdCap": "50" },
    "limits":  { "maxInputTokens": 8192, "maxOutputTokens": 4096 },
    "description": "Production Llama 3 8B"
  }'

Deployment phases

PhaseMeaning
PendingCR created; operator has not yet reconciled
PullingWeight files downloading from GCS / HuggingFace
VerifyingSHA256 digest check + cosign signature verification
RunningAt least one replica ready; gateway route active
ScaledToZeroKEDA has scaled replicas to 0 due to inactivity
BudgetPausedDaily spend exceeded the cap; manually resume with POST /resume
FailedUnrecoverable error; check status.conditions

Resume a budget-paused deployment

curl -X POST https://ai.acme.com/api/v1/deployments/{id}/resume \
  -H "Authorization: Bearer $ADMIN_TOKEN"

API Keys

API keys authenticate calls to the gateway. They are Argon2id-hashed before storage. The raw key is returned once at creation and cannot be retrieved again.

Create a key

bash
curl -X POST https://ai.acme.com/api/v1/keys \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"displayName": "prod-app"}'

# Response — save the key immediately:
{
  "key": "openserve_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "id":  "01HXY..."
}
🚨

The raw key is shown once and then discarded. Store it in a secret manager (e.g. GCP Secret Manager) immediately. If lost, rotate the key.

Rotate a key

curl -X POST https://ai.acme.com/api/v1/keys/{id}/rotate \
  -H "Authorization: Bearer $TOKEN"

Delete a key

curl -X DELETE https://ai.acme.com/api/v1/keys/{id} \
  -H "Authorization: Bearer $TOKEN"

Calling the Inference API

The gateway exposes an OpenAI-compatible API. Any SDK or tool that supports a custom base_url works without code changes.

curl (streaming)

bash
curl https://ai.acme.com/v1/chat/completions \
  -H "Authorization: Bearer openserve_live_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "model":    "llama-3-8b-instruct",
    "messages": [{"role": "user", "content": "Hello!"}],
    "stream":   true
  }'

Python (openai SDK)

python
from openai import OpenAI

client = OpenAI(
    base_url="https://ai.acme.com",
    api_key="openserve_live_xxx",
)

stream = client.chat.completions.create(
    model="llama-3-8b-instruct",
    messages=[{"role": "user", "content": "Explain BYOC."}],
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="", flush=True)

Using a LoRA adapter

# Set model= to the adapter name (not the base model ID)
client.chat.completions.create(
    model="my-finetuned-adapter",   # matches loraAdapters[].name in the CR
    messages=[...],
)

Rate Limits

Each API key has independent RPM (requests per minute) and TPM (tokens per minute) counters backed by a Redis sliding-window. Actual token counts (not estimates) are recorded after each response stream completes.

DefaultValue
RPM60 requests / minute
TPM100,000 tokens / minute

When a limit is exceeded, the gateway returns 429 Too Many Requests with a Retry-After header indicating when the oldest request expires from the window.

Adjusting limits

Currently via direct DB update or the GUI key editor. A PATCH /api/v1/keys/{id} endpoint with rpm/tpm body fields is on the v1.1 roadmap.

Budget Caps

A BudgetPolicy CRD enforces a daily USD spending ceiling per deployment. The operator polls BigQuery for actual spend every 5 minutes.

yaml — BudgetPolicy CRD
apiVersion: openserve.io/v1alpha1
kind: BudgetPolicy
metadata:
  name: llama-3-8b-budget
  namespace: openserve-inference
spec:
  deploymentRef: llama-3-8b-instruct
  dailyUsdCap: "50"
  monthlyUsdCap: "1000"       # optional
  alertThresholdPercent: 80   # alert (no pause) at 80% of cap

Or set it inline on the ModelDeployment:

spec:
  budget:
    dailyUsdCap: "50"
    alertThresholdPercent: 80

When the daily cap is breached, the deployment transitions to BudgetPaused and replicas scale to 0. Resume manually:

curl -X POST https://ai.acme.com/api/v1/deployments/{id}/resume \
  -H "Authorization: Bearer $ADMIN_TOKEN"

LoRA Adapters

Fine-tuned LoRA adapters can be hot-loaded into a running vLLM pod without redeployment. The operator calls the vLLM /v1/load_lora_adapter API after the deployment reaches Running phase.

yaml — ModelDeployment with LoRA
spec:
  modelRef: llama-3-8b-instruct
  loraAdapters:
    - name: acme-legal-v2         # use as model= in API calls
      path: gs://my-bucket/lora/acme-legal-v2
      baseModel: llama-3-8b-instruct
    - name: acme-support-v1
      path: gs://my-bucket/lora/acme-support-v1
      baseModel: llama-3-8b-instruct

Loaded adapters are tracked in status.loadedLoRAAdapters. Check:

kubectl get modeldeployment llama-3-8b-instruct \
  -n openserve-inference -o jsonpath='{.status.loadedLoRAAdapters}'

SGLang Engine

Set spec.engine: sglang to use SGLang instead of vLLM. SGLang is recommended for:

  • Structured generation (JSON mode, regex constraints)
  • Long-context workloads (128K+ token sequences)
  • Benchmarks where SGLang throughput exceeds vLLM
spec:
  modelRef: llama-3-8b-instruct
  engine: sglang   # default is "vllm"

The KEDA scaler automatically uses the SGLang metric (sglang:num_running_reqs) instead of the vLLM metric when engine: sglang is set.

RAG / Document Retrieval

openserve includes a built-in retrieval-augmented generation (RAG) pipeline backed by pgvector. Upload documents via the control-api; embeddings are stored in an IVFFlat index (cosine similarity, lists=100).

ℹ️

RAG requires an external embedding endpoint (e.g. a deployed nomic-embed-text-v1.5 deployment). Set EMBEDDING_ENDPOINT env var on the control-api.

Upload a document

curl -X POST https://ai.acme.com/api/v1/documents \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "title":   "Q4 2025 Product Spec",
    "content": "openserve v2 will add AWS EKS support..."
  }'

Retrieve relevant chunks

curl -X POST https://ai.acme.com/api/v1/rag/retrieve \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query": "AWS support timeline", "topK": 5}'

Prefix-Cache Routing

When a deployment has maxReplicas > 1, the operator writes per-pod IP addresses into the routing ConfigMap (podRoutes section). The gateway then uses FNV-1a consistent hashing on the system prompt prefix (first 512 chars) to route requests to the same pod — maximising the KV-cache hit rate and reducing TTFT.

This is automatic. No configuration is required. Falls back to service-VIP routing when only one replica exists.

Peer Relay

The peer-relay service enables external partner compute nodes to register as inference upstreams. Partners connect via WebSocket and receive inference requests routed through the gateway.

Create a peer

curl -X POST https://ai.acme.com/api/v1/peers \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "acme-hq-gpu-cluster", "description": "On-prem A100s"}'

Create an invite token

curl -X POST https://ai.acme.com/api/v1/peers/{id}/invites \
  -H "Authorization: Bearer $ADMIN_TOKEN"

Audit Log

Every action (login, key creation, deployment changes, member management) is written to the append-only audit_log table. Rows are never updated or deleted. Cloud Logging bucket lock provides WORM (write once, read many) guarantees.

curl https://ai.acme.com/api/v1/audit?limit=100 \
  -H "Authorization: Bearer $ADMIN_TOKEN" | jq '.entries[] | {action, actor, createdAt}'

Usage & Billing

Token usage and GPU-hour spend are streamed to BigQuery via the operator. The control-api aggregates this data for the usage dashboard.

curl https://ai.acme.com/api/v1/usage \
  -H "Authorization: Bearer $TOKEN"

Returns daily token counts, request counts, and USD spend per deployment for the last 30 days.

Security Hardening

💡

Enable Cloud Armor on the external load balancer with a rate-limit rule (e.g. 100 req/s per IP) as the first line of defence before traffic reaches the gateway.

  • Rotate the JWT secret regularly: update the jwt.secret Helm value and roll the pods.
  • Enable IP allowlisting on sensitive API keys via the key editor.
  • Set key expiry: short-lived keys (7–30 days) reduce blast radius if a key leaks.
  • Review audit logs weekly: look for unexpected create_api_key or remove_member entries.
  • Run govulncheck ./... in CI for each Go module: operator, apps/control-api, apps/gateway.
  • Keep engine images pinned: bump vllmImageTag in operator/internal/engine/vllm.go only after reviewing the vLLM changelog.

Troubleshooting

control-api won't start — "extension vector is not available"

Your Postgres instance doesn't have pgvector installed. In local dev, use pgvector/pgvector:pg16 as the postgres image. On Cloud SQL, enable the pgvector database flag.

gateway returns 503 — "deployment not found"

The routing ConfigMap doesn't have an entry for that deployment ID. Check that the deployment is in Running phase (kubectl get md -n openserve-inference) and that the operator has reconciled the route (kubectl get configmap openserve-routes -n openserve-system -o yaml).

Deployment stuck in "Pulling"

Weight download from GCS or HuggingFace is slow. Check the vLLM pod logs: kubectl logs -n openserve-inference -l app=vllm-llama-3-8b-instruct --tail=50. Ensure the GCS bucket is in the same region as your GKE cluster.

Rate limit returns 429 immediately

The key's RPM or TPM is set too low. List keys via GET /api/v1/keys to check current limits. Update via the GUI key editor or directly in Postgres (dev only).

go mod tidy fails — "go.mod requires go >= 1.24.1"

The control-api Dockerfile uses Go 1.24. Ensure your local Go version matches: go version. If building locally, run go install golang.org/toolchain@go1.24.1 or set GOTOOLCHAIN=auto.

Docker build fails on Apple Silicon

Add --platform linux/amd64 to the docker build command, or set DOCKER_DEFAULT_PLATFORM=linux/amd64 in your shell.

BudgetPaused — deployment keeps auto-pausing

Either the daily spend is genuinely exceeding the cap, or BigQuery has stale/incorrect data. Check status.todayUsdSpend on the ModelDeployment. To raise the cap, patch spec.budget.dailyUsdCap and resume.
